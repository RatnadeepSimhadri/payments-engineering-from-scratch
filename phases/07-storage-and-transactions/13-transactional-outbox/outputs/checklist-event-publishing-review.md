# Event Publishing Review Checklist

Use on any pull request where a handler writes a row and also sends a message, webhook, email, or RPC about that row. The pattern to look for is two writes to two systems in one code path. One unchecked box in the first two sections is a reason to request changes.

## The transaction boundary

- [ ] The business row and the event row are inserted in the same database transaction. No `publish()`, `send()`, HTTP call, or queue push appears between `BEGIN` and `COMMIT`, and none appears after `COMMIT` in the request path either.
- [ ] A rollback of the business write also removes the event. There is no code path where the event row commits and the business row does not.
- [ ] Framework hooks such as "after commit" listeners are not used as the durability mechanism unless they persist the event. If the listener only calls the broker, it is a dual write.
- [ ] The event payload is built from the same in-memory object as the business row, not by re-reading the row later.

## The event row

- [ ] Every event has an `eventId` assigned by the producer before commit, stable across every republish. It is not the broker offset, not a timestamp, and not generated by the relay.
- [ ] Every event has an `aggregateId` that becomes the broker partition key, so one entity's events stay in order.
- [ ] Every event has a `type` and a producer-side `createdAt`.
- [ ] The payload style is stated (thin, fat, or delta) and the consumer's obligations under that style are documented.
- [ ] Amounts in the payload are integers in minor units with a currency, or decimal strings. Never JSON numbers with fractions.

## The relay

- [ ] The relay reads pending rows in commit order (`ORDER BY seq` or the CDC stream) with a bounded batch size.
- [ ] The relay publishes first and marks second. Never the other way round.
- [ ] A broker failure on row N stops the batch; rows after N are not published until N succeeds or is quarantined.
- [ ] A per-row attempt counter and a dead-letter table exist for rows that fail permanently, with an alert when the table is non-empty.
- [ ] Multiple relay instances cannot publish the same row concurrently (`FOR UPDATE SKIP LOCKED`, a partition assignment, or a single leader), and the document says what ordering guarantee survives when there are several.
- [ ] Published rows are deleted or archived on a retention schedule, and there is an index that keeps the pending-row query fast regardless of table size.
- [ ] There is a metric for the oldest pending row's age and an alert on it. A growing age is a dead relay or a dead broker.

## The consumer

- [ ] The consumer deduplicates by `eventId` (or by a business key the event carries, such as a payment id that is unique on the consumer's own table).
- [ ] The consumer's effect and its "processed" marker are written in one transaction. A crash between them cannot cause a double apply.
- [ ] The dedupe set has a retention window longer than the longest plausible redelivery gap, or is keyed on data the consumer stores anyway.
- [ ] The consumer tolerates out-of-order events across different aggregates and either requires or does not require order within one aggregate; the document says which.
- [ ] There is a metric for duplicates ignored. A sudden rise means a relay is crash-looping or two relays are competing.

## Tests present in the PR

- [ ] A test that makes the broker unavailable during the request and asserts the request succeeds and the event is delivered later.
- [ ] A test that crashes the relay between publish and mark and asserts the consumer's state is correct after redelivery.
- [ ] A test that rolls back the business write and asserts no event is ever published.
- [ ] A test that publishes five events for one aggregate across more than one batch and asserts broker order equals commit order.

## Questions to ask the author

1. Point to the line where the broker is first contacted. Is it inside the request's database transaction, after it, or in a separate process?
2. If this handler runs, commits, and the pod is killed one millisecond later, what does the downstream system know?
3. If the relay publishes the same row twice, what does the consumer do, and how do you find out it happened?
