# AGENTS.md

Operating manual for contributors and AI agents touching this repository. Read it before writing a lesson or opening a PR.

The repository is a curriculum, not an application. The lessons are the product. Every rule below keeps the lessons coherent across three tracks and three implementation languages.

---

## Philosophy

Three tracks, sixteen phases, one spine: **build the mechanism from scratch, prove its invariant with a test, then compare it with the production equivalent.**

- **Track A — Data Structures & Algorithms** (Phases 0–4): the structures that databases, caches, schedulers, and ledgers are made of, built by hand and measured.
- **Track B — Distributed Systems** (Phases 5–9): clocks, consensus, replication, transactions, streams, and operations, each built on a deterministic simulated network so every bug is replayable.
- **Track C — Payments Engineering** (Phases 10–15): money, ledgers, rails, payment state machines, risk, and scale, built on the structures from A and the guarantees from B.

Every Build lesson ships the same implementation in **Java, Python, and Go**. The learner picks one language in `start-learning`; the tutor teaches in that language and only mentions the others when the difference is the lesson (memory model, decimal arithmetic, GC). The curriculum never asks a learner to switch languages to continue.

Examples are drawn from payments wherever they fit naturally: a hash map is an idempotency store, a heap is a retry scheduler, Dijkstra routes an FX conversion, a saga reserves and captures funds. The payments framing is motivation, not decoration; the data structure is still taught completely.

## Hard rules

1. **One commit per lesson directory.** A ten-lesson PR has ten commits. Subject: `feat(phase-NN/MM): <slug>` (≤72 chars). Body explains why, not what.
2. **Every Build lesson ships every CI language** (`languages.json`, `ci: true`). A lesson with Java only is `In Progress`, never `Complete`. Learn lessons ship no code but may include short illustrative snippets.
3. **Standard library only.** No build tools, no package managers, no frameworks. Java compiles with `javac`, Python runs with `python3`, Go runs with `go run .`. See the dependency table.
4. **Deterministic, self-terminating demos.** `main` prints a worked example and exits 0 in under ten seconds. No network, no stdin loops, no sleeping to simulate time: inject a clock.
5. **Mermaid or Markdown tables for diagrams.** No ASCII or Unicode box-drawing art.
6. **Every fenced code block carries a language tag.** Use `java`, `python`, `go`, `text`, `json`, `bash`, `console`, `mermaid`, `sql`, `xml`, `yaml`.
7. **Cite primary sources.** RFCs, ISO standards, network rulebooks, papers, and official docs. Never cite or copy from other curriculum repositories.
8. **Money is never a float.** Any lesson touching amounts uses the integer-minor-units `Money` discipline from Phase 10, Lesson 01, in all three languages (`long`/`BigDecimal`, `int`/`Decimal`, `int64`).
9. **Never commit generated files**: `catalog.json` is gitignored; `.out/` directories are gitignored; `README.md` Contents and `ROADMAP.md` are regenerated by `scripts/build_catalog.py`.
10. **Quizzes test the lesson, not trivia.** Distractors are plausible and comparable in length to the correct option. `scripts/audit_lessons.py` fails a quiz whose correct option is >40% longer than every distractor.

## Dependencies

| Language | Allowed | Canonical commands (run from `code/<lang>/`) |
|----------|---------|-----------------------------------------------|
| Java 21 | `java.*`, `javax.crypto` | `javac -d .out *.java && java -cp .out Main` · `java -cp .out MainTest` |
| Python 3.11+ | standard library (`decimal`, `dataclasses`, `unittest`, `hashlib`, `hmac`, `threading`, `asyncio`, `sqlite3`) | `python3 main.py` · `python3 -m unittest -v` |
| Go 1.22+ | standard library (`sync`, `context`, `crypto/*`, `encoding/*`, `testing`, `net`) | `go run .` · `go test ./...` |

Java tests use the tiny assertion harness pattern (`MainTest` with a `main` that counts failures and exits 1) because the JDK has no built-in test runner. Keep the harness in the test file itself so each lesson stays self-contained.

If a contribution needs a library, it is the wrong lesson design. Rewrite the lesson so the mechanism the library would provide is the thing being built.

## Lesson contract

### docs/en.md header

```markdown
# <Title>

> <One-line hook: the sentence a learner should remember a year later>

**Type:** <Learn | Build>
**Languages:** Java, Python, Go          <!-- must match the code/ folders present; "—" for Learn -->
**Prerequisites:** <comma-list of upstream lessons, or "None">
**Time:** ~<minutes> minutes

## Learning Objectives
- <4-6 bullets starting with a verb; each one testable by the quiz or the code>
```

### Required sections

Build lessons: `## The Problem`, `## The Concept`, `## Build It`, `## Use It`, `## Ship It`, `## Exercises`, `## Key Terms`, `## Further Reading`.
Learn lessons: `## The Problem`, `## The Concept`, `## Exercises`, `## Key Terms`, `## Further Reading` (plus `## Worked Example` where a trace helps).
Capstone lessons (Phase 15): `## The Problem`, `## What You Will Build`, `## Requirements`, `## Milestones`, `## Acceptance Criteria`, `## Rubric`, `## Further Reading`. A capstone is a project spec, not a tutorial: no code ships with it, every requirement names the lessons that teach the mechanism, and the rubric is what the `build-project` coach grades against.

Depth expectations for a Complete lesson:

- **The Problem** (2-4 paragraphs): a concrete failure. Name the system, the input, and what breaks. Prefer a payments scenario when it is natural.
- **The Concept** (the longest prose section): the mental model, the invariant, the complexity, and the trade-offs. Walk one worked example by hand with real numbers. Include a mermaid diagram or a comparison table. State what the structure *promises* and what it does not.
- **Build It**: step-by-step. Show the code in the **primary teaching language for that lesson** (usually Java, the course's first language) in chunks of 5–25 lines, each explained. Then a `### In Python` and `### In Go` subsection that shows only what differs (idioms, memory model, numeric types) and points to the full files. Every chunk must correspond to code that exists in `code/`.
- **Use It**: the standard-library or production equivalent (`java.util.HashMap`, `sorted`, `sync.Map`, PostgreSQL, Kafka, Stripe's API shape), and specifically what it does that the from-scratch version made explicit.
- **Ship It**: the artifact in `outputs/` — a checklist, a design-review template, an interview card, a runbook — written so the learner can use it at work on Monday.
- **Exercises**: three, graded easy / medium / hard, with the hard one combining a previous lesson.
- **Key Terms**: a 4-10 row table: term, what people say, what it actually means. Every term must have an entry in `glossary/terms.md`.
- **Further Reading**: 3-8 primary sources with one line each on why; every entry carries a URL (publisher page or DOI for books and papers).

Target length: 350–700 lines for a Build lesson, 250–450 for a Learn lesson. Depth comes from worked examples, invariants, and failure modes, not from adjectives.

### quiz.json

```json
{
  "lesson": "<dir-slug>",
  "title": "<Lesson Title>",
  "questions": [
    {"stage": "pre",   "question": "...", "options": ["a", "b", "c", "d"], "correct": 0, "explanation": "..."},
    {"stage": "check", "question": "...", "options": ["a", "b", "c", "d"], "correct": 1, "explanation": "..."},
    {"stage": "check", "question": "...", "options": ["a", "b", "c", "d"], "correct": 2, "explanation": "..."},
    {"stage": "check", "question": "...", "options": ["a", "b", "c", "d"], "correct": 1, "explanation": "..."},
    {"stage": "post",  "question": "...", "options": ["a", "b", "c", "d"], "correct": 3, "explanation": "..."},
    {"stage": "post",  "question": "...", "options": ["a", "b", "c", "d"], "correct": 0, "explanation": "..."}
  ]
}
```

Exactly six questions: one `pre` (activates prior knowledge before reading), three `check` (asked mid-lesson by the tutor), two `post` (the end-of-lesson quiz). `correct` is zero-indexed. Spread the correct index across positions: no index may be correct for more than two of the six questions, and explanations must not refer to options by position ("the second option") so options can be reordered. Explanations say why the right answer is right *and* why the strongest distractor is wrong.

### code/

- `Main.java` / `main.py` / `main.go` implement the lesson's mechanism and print a worked example in `main`.
- Header comment (4-6 lines) cites `phases/NN-.../MM-.../docs/en.md`, states the canonical run and test commands, and cites any spec or paper.
- Tests: **8+ assertions** per language covering the happy path, the invariant, at least one boundary, and at least one failure the lesson warns about. Java tests in `MainTest.java` (self-contained harness), Python in `test_main.py` (`unittest`), Go in `main_test.go`.
- The three implementations are **the same design**, not three idiomatic rewrites: same type names where the language allows, same method names, same test cases. A learner who switches languages later should recognize everything.
- Java: no packages, so `javac -d .out *.java` works; helper types may live in extra files. Go: one `package main` per lesson with its own `go.mod` (`module pefs/<phase>/<lesson>`). Python: a single `main.py` unless the lesson is explicitly about modules.
- Time, randomness, and I/O are injected (a `Clock`, a seeded `Random`, an in-memory `Network`) so demos and tests are deterministic.

## Project contract

See `projects/AUTHORING.md`. In short: a `project.json` with ordered stages; stage 1 ships a `starter/<lang>/` for every language the project supports; every stage ships `tests/<lang>/`; `solution/<lang>/` passes every stage. Learners never read `solution/`; the `build-project` skill enforces this.

---

## Skills contract

`skills/<name>/SKILL.md` is the portable source. `.claude/skills/<name>/SKILL.md` is an identical copy for Claude Code discovery; `python3 scripts/sync_skills.py` copies them and `--check` fails CI when they drift. Skills never hard-code lesson lists; they read `README.md` Contents, `curriculum/curriculum.json`, or a manifest in `learning-paths/`. Every skill honours the **language choice recorded in `LEARNING.md`** and renders host-specific invocation syntax (Claude Code `/learn`, Codex `learn`, other hosts natural language).

## Per-PR validation

```bash
python3 scripts/audit_lessons.py                     # lesson invariants, blocking
python3 scripts/build_catalog.py --check             # README/ROADMAP in sync
python3 scripts/sync_skills.py --check               # skills mirrored
python3 scripts/run_lesson.py phases/NN-.../MM-...   # run + test the lesson you touched in all 3 languages
python3 scripts/project_test.py <id> --lang java --all --solution   # when a project changes; repeat per language
```

CI (`.github/workflows/curriculum.yml`) runs the audit and every lesson in every language on pull requests, and regenerates README/ROADMAP on pushes to `main`.

## New-lesson workflow

```bash
python3 scripts/scaffold_lesson.py 10 3        # phase 10, lesson 3, from curriculum.json
# 1. Write docs/en.md to the contract above.
# 2. Replace the stub in code/java, code/python, code/go; same design in each.
# 3. Write 8+ tests per language.
# 4. Fill quiz.json (6 questions).
# 5. Add outputs/ artifact if the lesson ships one.
python3 scripts/run_lesson.py phases/10-money-and-ledgers/03-double-entry-ledger
python3 scripts/audit_lessons.py --phase 10
python3 scripts/build_catalog.py
git add phases/10-money-and-ledgers/03-double-entry-ledger README.md ROADMAP.md
git commit -m "feat(phase-10/03): double-entry-ledger"
```

To add a lesson that is not yet in `curriculum/curriculum.json`, add it there first (keep numbering contiguous), then scaffold.
